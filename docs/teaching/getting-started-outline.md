## 一、文章定位与写作约定

**面向读者：** 初次接触编程的大学一年级学生。默认读者能使用浏览器和安装普通软件，但不预设其理解路径、终端、编译器或 OJ。

**核心任务：** 在自己的电脑上编写、编译、运行并测试一个 C++ 程序，完成第一次课程 OJ 提交；遇到问题时，能够查资料或提供足够的信息求助。

**阅读路线：**

```text
准备练习文件夹
→ 按操作系统配置环境
→ 编译和运行
→ 输入、输出与本地测试
→ 查资料与求助
→ OJ 提交与反馈
→ 完成检查
```

写作约定：

- 先写操作步骤和预期结果；基础概念在首次用到的位置用几句话解释，不设置系统性的基础科普章节。
- 搜索与求助以具体案例和可复制模板讲解，术语背景简短交代。
- 每组操作说明写清：在哪里操作、做什么、预期看到什么、失败时查看哪一项。
- 区分“命令”“终端显示的结果”和“程序输入”，避免学生把三者一起复制。
- Windows、macOS、Linux 分别给出明确步骤；Windows 提供更细的操作说明与故障示例，另外两平台保留完整的必要步骤。学生只需阅读自己的平台分支。
- 先用命令行走通一次真实编译流程，再介绍编辑器快捷操作。
- 示例以普通代码块和本地操作为主。浏览器运行示例仅作补充。
- 鼓励自主排查，也明确告诉学生：初学者不知道怎么搜索时，可以直接求助。

**范围边界：** 本章只解释支撑操作所需的基础概念和最少量 C++ 语法。进程、内存、编码、权限等不另设科普小节；CPU 原理、二进制、操作系统内部机制、系统性的调试器教学、Git、构建系统和多文件项目留到后续材料。可用配置可包含最小运行/调试入口。LaTeX 只介绍插件用途、安装前提和基本配置，不讲排版语法或完整工具链安装。

#### 2.5 使用配套配置文件

**交付要求（已确认）：** 仅提供 Windows 的完整配置包，放在仓库的示例目录，正式稿链接对应工具链目录和文件，并说明复制到哪里、安装前提、默认工具路径和验证步骤。篇幅很短的配置可附在文末；较长配置通过仓库链接提供。macOS/Linux 使用手动命令。

本节先说明配置的位置与用途；建议学生在第 3 节手动编译成功后再应用快捷运行配置。

拟提供的配置包结构：

```text
cpp-starter/windows-<winlibs 或 msys2>/
├── main.cpp
└── .vscode/
    ├── extensions.json        # 插件推荐
    ├── settings.json          # 最少量编辑器设置
    ├── c_cpp_properties.json  # 编译器、标准与代码提示
    ├── tasks.json             # 编译与终端运行任务
    └── launch.json            # 最小运行/调试入口
```

- Windows 提供 WinLibs 主线配置与 MSYS2 补充配置，分别使用与安装示范一致的工具路径。
- 明确“打开文件夹 → 放置或解压配置 → 打开并保存源文件 → 编译 → 运行”的步骤；编译仍先在第 3 节演示一次手动命令。
- 默认路径必须与安装示范一致；若安装位置不同，指出需要修改的具体字段。
- 编译命令和任务显式使用 `-std=c++20`，代码提示标准与之保持一致；不声称这是尚未核实的 OJ 要求。
- 检查编译任务失败后的行为，运行入口避免默默执行旧程序；确认终端能够接收 `std::cin` 输入。
- Code Runner 提供 Windows 工作区配置：启用 `code-runner.runInTerminal`、`code-runner.saveFileBeforeRun`、`code-runner.ignoreSelection`、`code-runner.fileDirectoryAsCwd`，关闭 `code-runner.preserveFocus`，便于输入并始终运行已保存的完整文件。
- `code-runner.executorMap` 显式设置本课使用的编译器、标准、文件路径引用和编译成功后才执行的逻辑；Windows 按所选 Shell 单独配置，避免依赖默认命令在所有终端中都可用。
- 正文用“Run Code”明确指认 Code Runner 入口，说明它与 C/C++ 插件的运行/调试入口不同；在首次手动编译成功后再介绍快捷运行。
- LaTeX 配置放在独立示例目录，正文仅给链接和基本配置方法；明确对应 TeX 工具前提。
- C++ 的默认 `extensions.json` 只推荐主线 C/C++ 扩展；Code Runner、LaTeX 和中文语言包按用途另行介绍，方便学生按需安装。

#### 3.3 编译，再运行

- 分平台给出完整命令，逐项解释源文件名、输出文件名和必要参数。
- 本地命令使用 C++20，并简短说明标准参数；课程 OJ 支持的标准另行核实。

**完成标志：** 能说明程序需要什么输入，并判断一次运行结果是否正确。

### 5. 遇到问题时：观察、查阅、搜索与求助

**目标：** 建立可操作的问题解决习惯，降低第一次排查问题的门槛。

#### 5.1 先确定是哪一步失败

- 按安装、寻找文件、编译、运行、结果五个环节定位。
- 保留原始命令和完整错误信息，优先查看第一条相关错误。
- 区分环境问题与代码问题；不把所有失败都归结为“软件坏了”。

#### 5.2 STFW 与 RTFM：具体应该怎么做

- 解释 STFW（Search The Web）和 RTFM（Read The Manual）所指的查阅习惯。
- 说明这两个缩写的常见展开带有粗俗或不友善的表达；本文使用温和说法介绍方法。
- 搜索式从“工具名称 + 关键报错 + 操作系统”开始，示范如何去掉个人路径等干扰信息。
- 原始英文报错可以直接用于搜索，不必先翻译成含糊的描述。
- 阅读官方文档中的安装要求、操作步骤和故障说明；根据问题选择相关部分。
- 核对资料的平台、版本和上下文，理解命令后再执行。
- 每次只尝试一个修改，记录结果；没有变化时回到原假设检查。

#### 5.3 一个完整的搜索案例

以“找不到编译器命令”为例，按平台展示真实报错：

```text
记录现象
→ 提取关键词
→ 找到适用的说明
→ 检查是否安装及能否找到编译器
→ 做一个修改
→ 重新验证版本
```

案例使用几种可能原因组织检查，避免暗示一条搜索结果能解决所有同名报错。

#### 5.4 选择合适的信息来源，并使用 AI 辅助排查

用一张简短比较表帮助学生选择下一步：

| 途径 | 本章中的用途 | 需要核对什么 |
| --- | --- | --- |
| 搜索引擎 | 从报错和关键词查找相关文档与已有讨论 | 平台、版本、问题上下文 |
| 官方文档 | 确认安装要求、配置字段和工具行为 | 是否对应正在使用的工具版本 |
| AI | 解释陌生报错、组织搜索词、列出检查步骤 | 推测是否有依据，建议能否在本机验证 |
| 向老师、助教或同学求助 | 获取课程特定信息，或共同检查难以定位的问题 | 是否已提供足够的复现信息 |

- 不规定必须按某个顺序使用所有途径；根据当前问题选择。
- 以“找不到编译器”或前文分号错误为例，提供带环境、完整命令、报错和目标的 AI 提问示范。
- 要求解释原因与检查步骤，帮助理解建议涉及的操作；把推测转为能够观察的检查项。
- 对照工具文档，逐项尝试并重新编译运行，记录结果；新的错误也应原样保留。
- AI 不能直接看到未提供的电脑环境；示范如何补充信息，而不是反复只说“还是不行”。
- 简短提醒课程作业中的使用范围以课程规定为准，不替课程制定尚未确认的 AI 政策。
- 不介绍特定产品、订阅或模型；本节围绕通用排查方法。

#### 5.5 如何提出一个容易回答的问题

- 问题描述包含：目标、环境、操作步骤、实际结果、预期结果、已尝试的方法。
- 命令、代码和报错尽量以可复制的文本提供；界面位置问题可以配截图。
- 代码问题尽量保留一个能复现的最小例子，同时给出输入。
- 提供一个含糊问题与一个完整问题的对照。
- 明确可以求助的时机：不知道如何开始、读不懂搜索结果、尝试后仍卡住；不设置求助前的硬性搜索次数。

**可复制的求助模板：**

```text
我想完成：
操作系统、工具和版本：
当前文件位置与执行的命令：
相关代码或复现步骤：
测试输入（如有）：
预期结果：
实际结果与完整报错：
我已经尝试了什么，结果如何：
```

**动手任务：** 整理第 3 节的编译错误，写出一个搜索式和一段可用于 AI 或助教排查的问题描述；选择一种途径检查建议并验证结果。

**完成标志：** 能准确描述故障，并提出有针对性的搜索或求助。

### 6. 使用课程 OJ：完成第一次提交

**目标：** 了解评测机制，能够找到题目、提交程序并查看对应记录。

**第一版范围（已确认）：** 提供通用操作路线和需要检查的信息，不指定真实按钮、网址或账号规则。课程入口、截图与具体规定留待后续补充；通用示意明确标注，不作为内部 OJ 的实测步骤。

#### 6.1 OJ 如何评测你的程序

- 解释 OJ 在自己的环境中编译和运行提交内容，再根据题目规则判断结果。
- 用“提交程序 → 编译 → 测试输入 → 检查输出 → 反馈”说明流程。
- 区分样例与其他评测数据，以及本地环境与 OJ 环境。

#### 6.2 登录并找到课程题目

- 第一版：说明应通过课程提供的入口访问，并查阅账号、网络访问和课程加入说明。
- 第一版：讲解从课程或作业列表找到题目的一般思路，不虚构页面名称。
- 后续补充：准确入口、访问条件、账号方式、实际页面路径与关键截图。

#### 6.3 阅读题面

- 按问题要求、输入格式、输出格式、数据范围、时间与内存限制解释阅读顺序。
- 用自拟的两数相加练习说明这些字段；课程实际题目只引用题号和入口。
- 不额外打印提示语；依据题目规定处理大小写、空格和换行。
- 区分单组输入、多组输入和读到 EOF；首次练习按实际题目说明，其他情况留作提醒。

#### 6.4 提交前的检查

- 本地测试通过，且提交的是已保存的正确代码版本。
- 确认语言和标准，以及是否需要完整程序或其他提交形式。
- 检查是否残留调试输出、仅在本地使用的文件路径或不必要的依赖。
- 按实际要求提交源代码，而不是误交可执行文件。

#### 6.5 提交并找到评测记录

- 第一版：说明按页面要求粘贴或上传源代码，选择支持的语言，并找到本次提交记录。
- 用通用示意展示题号、提交时间、状态与本次代码的关联。
- 提醒学生查阅截止时间、计分方式和重复提交规则。
- 后续补充：真实页面操作、语言选项、结果页面与核实后的课程规定。

**练习：** 第一版以同一个“两数相加”示例展示通用提交过程。后续补充实际 OJ 对应题号或练习时，再核对输入约定并完成真实提交；不虚构平台已有该题。

**完成标志：** 能找到自己的提交记录，并确认它对应哪份程序。

### 7. 看懂评测结果，决定下一步

**目标：** 将评测反馈转化为具体排查行动。

| 常见反馈（待与课程 OJ 核对） | 正文解释方向 | 首先尝试的行动 |
| --- | --- | --- |
| 等待 / 评测中 | 暂无最终结论 | 查看该提交状态，不立即反复重交 |
| AC | 通过当前评测 | 确认题目、提交版本和课程完成状态 |
| CE | 编译失败 | 阅读诊断，检查提交语言与代码 |
| WA | 结果不符合要求 | 检查题意、输出格式和反例 |
| RE | 运行异常 | 排查越界、除零等问题 |
| TLE | 超过时间限制 | 检查死循环和计算量 |
| MLE | 超过内存限制 | 检查数据结构大小与分配 |

- 状态名称、缩写和含义以实际平台为准，不预设平台支持所有状态。
- 用一个小案例说明“本地能运行”“样例通过”“OJ 通过”分别提供什么证据。
- 首次练习以 CE 和 WA 为重点；时间、空间复杂度只建立初步意识。

**完成标志：** 学生能根据结果指出下一项检查，而不是只说“没通过”。

### 8. 完成检查与下一步

以可勾选清单结束正文：

- [ ] 我能找到自己的源文件，知道终端当前在哪里。
- [ ] 我能验证编译器可用，独立完成编译与运行。
- [ ] 我能修改、保存、重新编译，并运行更新后的程序。
- [ ] 我能提供输入，预先计算结果并进行比较。
- [ ] 我能保留报错，组织搜索词或写出可复现的问题描述。
- [ ] 我能提交到课程 OJ，找到记录并理解评测反馈。

**下一步：** 引导学生继续学习基本类型、表达式和控制流程；后续单独讲解断点调试与更系统的测试。

## 三、文末查阅区

### A. 常见问题速查

每条采用“现象 → 可能原因 → 检查步骤 → 成功标志”的形式，链接回正文对应步骤。

优先覆盖：

- 找不到编译器命令。
- 编译器找不到 `main.cpp`。
- 保存成了错误的扩展名。
- 编译没有输出，不知道是否成功。
